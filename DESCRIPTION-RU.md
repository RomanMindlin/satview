# Как работает satview

satview скачивает свежие спутниковые снимки из семи источников и превращает каждый из них в
картинку одного вида: изображение Израиля в видимом свете, на котором видны облака. У всех
картинок одна и та же область, одна картографическая проекция и один стиль: береговые линии,
границы и подпись с временем съёмки.

В этом документе описан весь путь от команды `satview run` до PNG-файла на диске:

- какие запросы программа отправляет каждому серверу спутниковых данных и что получает в ответ;
- какие форматы файлов она читает;
- какие алгоритмы выбирают снимки, исправляют физические искажения и строят цвета;
- как рисуется и сохраняется итоговая картинка.

Установка и повседневное использование описаны в [README](README.md). Ссылки на код ниже ведут
к модулям в [satview/](satview/).

## 1. Общая схема

```
 satview run
     │
     ▼
 config.yaml + .env + флаги CLI ──► Config (проверенный)          satview/config.py
     │
     ▼
 целевая сетка: UTM 36N, 500 м (или мельче)                       satview/areas.py
     │
     ▼  для каждого включённого источника
 ┌────────────────────────── адаптер источника ──────────────────┐ satview/sources/*.py
 │ find()      поиск в каталоге сервера, выбор снимков            │
 │ download()  скачивание только нужных файлов (или их частей)    │ → cache/<source>/…
 │ load()      калибровка, коррекции, сборка RGB, пересчёт на     │ → Image (RGBA на сетке)
 │             сетку, растяжение контраста                        │
 └────────────────────────────────────────────────────────────────┘
     │
     ▼  общая часть для всех источников                           satview/pipeline.py
 пропуск, если уже готово · пропуск ночью · необязательная подстройка цвета
     │
     ▼                                                            satview/render.py
 чёрный фон · масштаб до width_px · берега/границы/города · подпись
     │
     ▼
 output/<source>/<дата>/<source>[_<спутник>]_<YYYYMMDDTHHMM>.png  (+ .tif, .gif, .mp4)
```

Каждый модуль-источник умеет общаться с одним сервером данных и читать один формат файлов.
Всё, что происходит после `load()`, общее, поэтому снимки всех спутников можно сравнивать
рядом друг с другом.

### Семь источников

| Источник | Спутник / прибор | Орбита | Сервер | Вход |
| --- | --- | --- | --- | --- |
| `meteosat12_fci` | Meteosat-12, FCI | геостационарная, 0° | EUMETSAT Data Store | API-ключ + секрет |
| `meteosat9_iodc` | Meteosat-9, SEVIRI | геостационарная, 45,5° в. д. | EUMETSAT Data Store | API-ключ + секрет |
| `viirs_gibs` | NOAA-20 / Suomi NPP, VIIRS (готовое изображение) | полярная | NASA GIBS (WMS) | не нужен |
| `viirs_l1b` | Suomi NPP, NOAA-20, NOAA-21, VIIRS | полярная | NASA CMR + LAADS / LANCE | Earthdata |
| `sentinel3_olci` | Sentinel-3A/B, OLCI | полярная | Copernicus Data Space (OData) | учётная запись CDSE |
| `sentinel2_msi` | Sentinel-2A/B/C, MSI L2A | полярная | Earth Search на AWS (STAC + COG) | не нужен |
| `landsat_oli` | Landsat 8/9, OLI L2 | полярная | Microsoft Planetary Computer (STAC + COG) | анонимный токен |

Геостационарный спутник висит над одной точкой экватора и каждые 10–15 минут снимает весь
видимый диск Земли. Спутник на полярной орбите летает низко и видит каждое место один-два раза в
сутки, зато гораздо детальнее. Для этих двух типов нужна разная логика поиска (раздел 4).

## 2. Один запуск, шаг за шагом

### 2.1 Конфигурация

[config.py](satview/config.py) собирает один проверенный объект `Config`:

1. Читает `config.yaml`. В этом файле никогда нет секретов, только *имена* переменных
   окружения, в которых они хранятся (например, `key_env: EUMETSAT_KEY`).
2. Загружает в окружение файл `.env`, лежащий рядом с конфигом. Переменные, уже заданные в
   окружении, имеют приоритет.
3. Накладывает флаги командной строки поверх YAML как ключи через точку:
   `--set output.width_px=800`; `--at …` превращается в `time.mode=at` и `time.at=…`;
   `--source X` включает источник X и выключает все остальные; и так далее.
4. Pydantic проверяет результат. Неизвестные ключи считаются ошибкой. Время разбирается как
   UTC. В диапазоне времени не может быть больше 1000 шагов; время в будущем отвергается.
5. Относительные пути отсчитываются от папки конфига, поэтому задание cron пишет туда же, куда и
   ручной запуск. Для областей, отличных от `israel`, создаётся своя подпапка `output/<area>/`.

Ещё до любого сетевого обмена `check_credentials()` проверяет, что переменные окружения
выбранных источников заданы. Если какой-то не хватает, программа завершается с кодом 2.

### 2.2 Выбор времени

`TimeSpec` ([base.py](satview/sources/base.py)) описывает, что попросил пользователь:

| Режим | Смысл | Целевые моменты («слоты») |
| --- | --- | --- |
| `latest` | самый свежий доступный сейчас снимок | `[now]` |
| `at` | снимок, ближайший к заданному времени UTC | `[at]` |
| `range` | по одному снимку на каждый шаг от начала до конца | `start, start+step, …, end` |

Каждый источник превращает это в окно поиска на своём сервере (раздел 4). Для геостационарных
источников функция `select_times()` затем выбирает:

- для `latest` — самый новый продукт;
- иначе для каждого слота — ближайший к нему продукт, но только если он попадает в допуск
  (10 мин для FCI, 15 мин для SEVIRI). Один и тот же продукт не используется дважды, поэтому
  шаг 5 минут при данных раз в 15 минут не даёт повторяющихся кадров.

### 2.3 Целевая сетка

Все источники пересчитываются на одну сетку, заданную в [areas.py](satview/areas.py):

- **Проекция:** UTM, зона 36N (EPSG:32636). Расстояния в ней — настоящие метры, а программы,
  читающие GeoTIFF, знают этот код EPSG.
- **Области:**

  | Область | Прямоугольник lon/lat | Сетка 500 м | PNG при `width_px: 1200` |
  | --- | --- | --- | --- |
  | `israel` | 33,8–36,2° в. д., 29,0–33,6° с. ш. | 476 × 1029 пикс. | 1200 × 2594 пикс. |
  | `israel_north` | 34,0–36,0° в. д., 30,4–33,6° с. ш. | 392 × 717 пикс. | 1200 × 2195 пикс. |

- **Как вычисляются границы:** на каждой из четырёх сторон прямоугольника lon/lat берётся по
  50 точек, чтобы изогнутые после перепроецирования края не потерялись. Точки переводятся в
  UTM. Затем минимум и максимум по x и y округляются наружу до целых пикселей. Для `israel`
  получается x 574 000–812 000 м и y 3 208 000–3 722 500 м.
- **Более мелкие сетки:** Sentinel-2 и Landsat используют те же границы с шагом `resolution_m`
  (по умолчанию 100 м, то есть 2376 × 5142 пикселей для `israel`). Картинки всё равно точно
  совпадают с картинками других источников.

Сетка — это объект pyresample `AreaDefinition`, на который Satpy умеет пересчитывать данные.

### 2.4 Обработка одного снимка

`pipeline.process()` ([pipeline.py](satview/pipeline.py)) обрабатывает один снимок («гранулу»):

1. **Уже сделано?** Если все запрошенные выходные файлы существуют, снимок пропускается
   (статус `exists`). Флаг `--force` отключает эту проверку.
2. **Проверка светлого времени.** Высота Солнца вычисляется функцией
   `pyorbital.astronomy.sun_zenith_angle` в центре области (35,0° в. д., 31,5° с. ш. для
   `israel`). Если Солнце ниже 5°, видимые каналы слишком темны и бесполезны, снимок
   пропускается (статус `night`). Суточные композиты (GIBS) эту проверку не проходят.
3. **Скачивание** в `cache/<source>/<id гранулы>/` (своё для каждого источника, раздел 3).
4. **Загрузка** в `Image`: массив RGBA uint8 размером `(строки, столбцы, 4)` на целевой сетке.
   Альфа 0 означает «нет данных» (раздел 5).
5. **Необязательная подстройка цвета** (`enhance:` в конфиге, раздел 5.7).
6. **Отрисовка** и сохранение PNG и/или сохранение GeoTIFF (раздел 6).

Для диапазона времени `pipeline.animate()` затем собирает из PNG-файлов GIF и/или MP4.

## 3. Сетевой обмен с серверами спутниковых данных

### 3.1 Общий HTTP-слой

[net.py](satview/net.py) и [cache.py](satview/cache.py) дают всем источникам одинаковое
поведение:

- **Одна сессия `requests.Session`** с заголовком `User-Agent: satview/0.1.0`. Тайм-ауты:
  15 с на соединение и 120 с на чтение.
- **Повторы на уровне транспорта** (urllib3 `Retry`): до 4 повторов для GET и POST при HTTP 429,
  500, 502, 503 и 504, с экспоненциальной задержкой (коэффициент 2).
- **Повторы на уровне операции** (`net.retry`): весь поиск или всё скачивание целиком
  выполняется до 3 раз, с паузами 5 с и затем 10 с. Это покрывает и клиентские библиотеки,
  у которых своих повторов нет (eumdac, earthaccess).
- **Атомарное скачивание** (`cached_file`): данные пишутся порциями по 1 МиБ в `<имя>.part`.
  Файл переименовывается в `<имя>` только после того, как скачан полностью. Поэтому прерванная
  загрузка никогда не выглядит как готовый файл в кэше, и следующий запуск начнёт её заново.
- **Распознавание страниц входа.** Если сервер вместо данных отвечает с
  `Content-Type: text/html`, скачивание завершается ошибкой с понятным сообщением. Обычно это
  значит, что перенаправление привело на страницу входа или лицензии.
- **Авторизация при перенаправлениях.** По умолчанию `requests` убирает заголовок
  `Authorization`, когда перенаправление ведёт на другой хост. Именно это нужно для LAADS
  (VIIRS): он перенаправляет в хранилище, которое этот заголовок отвергает. CDSE (OLCI) нужно
  обратное. С `keep_auth_on_redirect=True` satview сам проходит до 5 перенаправлений и каждый
  раз отправляет заголовок.

### 3.2 EUMETSAT Data Store (Meteosat-12 FCI, Meteosat-9 SEVIRI)

Общий код: [eumetsat.py](satview/sources/eumetsat.py). Он использует библиотеку `eumdac`,
которая делает такие HTTP-запросы:

| Шаг | Запрос | Примечания |
| --- | --- | --- |
| Токен | `POST https://api.eumetsat.int/token`, HTTP Basic `key:secret`, форма `grant_type=client_credentials` | Возвращает bearer-токен и `expires_in`. eumdac обновляет его до истечения срока. |
| Поиск | `GET https://api.eumetsat.int/data/search-products/1.0.0/os?format=json&pi=<коллекция>&dtstart=…&dtend=…&si=0&c=<размер страницы>` | OpenSearch. Возвращает объекты GeoJSON, по одному на продукт. Время передаётся как UTC без смещения (`2026-10-31T10:00:00`). |
| Список файлов | `GET https://api.eumetsat.int/data/browse/1.0.0/collections/<коллекция>/products/<id>?format=json` | Перечисляет файлы («entries») внутри продукта. |
| Скачивание одного файла | `GET https://api.eumetsat.int/data/download/1.0.0/collections/<коллекция>/products/<id>/entry?name=<файл>` | Bearer-токен. satview скачивает отдельные файлы, никогда не весь zip продукта. |

Используемые коллекции ([constants.py](satview/sources/constants.py)):

- `EO:EUM:DAT:0662`: FCI Level 1c, обычное разрешение (FDHSI, видимые каналы 1 км), точка 0°.
- `EO:EUM:DAT:0665`: FCI Level 1c, высокое разрешение (HRFI, красный канал 500 м), точка 0°.
- `EO:EUM:DAT:MSG:HRSEVIRI-IODC`: SEVIRI Level 1.5 над Индийским океаном.

Продукты FCI дополнительно фильтруются по `MTI1+` в идентификаторе продукта (Meteosat-12).
В будущем в той же коллекции могут оказаться и другие спутники MTG-I.

#### Ограничение лицензии

Бесплатная учётная запись EUMETSAT может *искать* все продукты. Но *скачивать* в реальном
времени она может только ежечасные сканы (начинающиеся в 00 минут). По политике данных EUMETSAT
эти ежечасные сканы относятся к данным «Core». На любой другой скан сервер отвечает
`403 "NRTLicense required"`, пока ему не исполнится час. Поэтому `downloadable()` оставляет
продукт, если его скан начался в 0 минут или если он начался не менее 61 минуты назад (час плюс
запас на расхождение часов). Окна поиска для `latest` сделаны достаточно широкими, чтобы в них
всегда был такой продукт:

- FCI: от now − (40 мин + 61 мин) до now;
- SEVIRI: от now − (60 мин + 61 мин) до now.

В режимах `at` и `range` окно — это запрошенное время ± 10 мин (FCI) или ± 15 мин (SEVIRI).

#### Meteosat-12 FCI: скачиваются только полосы над Израилем

Продукт FCI на весь диск разбит на 40 файлов-полос «BODY», пронумерованных с юга (1) на север
(40), плюс файл «TRAIL». Всего около 1 ГБ. Израиль попадает лишь в несколько полос строк.
`fci_chunks()` ([meteosat12_fci.py](satview/sources/meteosat12_fci.py)) находит их так:

1. Накладывает сетку 20 × 20 точек на границы области в lon/lat.
2. Переводит точки в геостационарную проекцию FCI
   (`+proj=geos +lon_0=0 +h=35786400 +ellps=WGS84 +sweep=y`) и берёт координату `y`. Если точка
   не видна из 0°, результат получается не конечным, и область отвергается.
3. Переводит `y` в долю высоты диска: `f = (y + 5 568 000) / (2 × 5 568 000)`, где 0 —
   южный край. 5568 км — это половина размера полного диска из определения области FCI в Satpy.
4. Номер полосы = `floor(f × 40) + 1`. Берётся диапазон от наименьшего номера до наибольшего,
   плюс ещё по одной полосе с каждой стороны, потому что реальная высота полос отличается на
   несколько строк.

Для обеих областей получаются полосы **30–33**: 4 файла из 40, примерно по 29 МБ, то есть около
115 МБ на скан вместо ~1 ГБ. Имена файлов соответствуют шаблону `…-BODY-…_00NN.nc`. Файл TRAIL
не нужен.

#### Meteosat-9 SEVIRI

Каждый скан IODC — это один файл `.nat` на весь диск (~180 МБ). Разделить его нельзя, поэтому
он скачивается целиком.

#### Проверка доступа

`satview list-sources` запрашивает токен (при неверных учётных данных здесь будет ошибка) и
читает название коллекции.

### 3.3 NASA GIBS (`viirs_gibs`)

GIBS отдаёт готовые суточные мозаики в истинных цветах через открытый сервис OGC WMS. Вход не
нужен. [viirs_gibs.py](satview/sources/viirs_gibs.py) делает запросы одного вида:

```
GET https://gibs.earthdata.nasa.gov/wms/epsg4326/best/wms.cgi
    ?SERVICE=WMS&REQUEST=GetMap&VERSION=1.3.0
    &LAYERS=VIIRS_NOAA20_CorrectedReflectance_TrueColor&STYLES=
    &CRS=EPSG:4326&BBOX=<lat_min>,<lon_min>,<lat_max>,<lon_max>   ← WMS 1.3: сначала широта
    &WIDTH=1065&HEIGHT=1890&FORMAT=image/png&TRANSPARENT=TRUE
    &TIME=2026-10-30
```

- **Прямоугольник:** границы целевой сетки в lon/lat, расширенные на 0,02° и округлённые до
  0,01°, чтобы прямоугольник (и ключ кэша) не менялся. Для `israel` это 33,73–36,39° в. д.,
  28,94–33,66° с. ш.
- **Размер:** 0,0025° на пиксель (~250 м, примерно собственное разрешение слоя), то есть
  1065 × 1890 пикселей для `israel`.
- **Ответ:** PNG в равнопромежуточной проекции (регулярная сетка lon/lat). Где данных нет,
  пиксели прозрачные или чёрные. Если в ответ пришло не изображение, показывается текст ошибки.
- **Какой день для `latest`:** изображение над Израилем строится по полуденному пролёту
  (~10–12 UTC). Утром сегодняшнее изображение ещё пустое. Сначала satview запрашивает миниатюру
  сегодняшнего дня шириной 48 пикселей. Если данные есть хотя бы в 95 % её площади, берётся
  сегодняшний день, иначе — вчерашний.
- **Правила покрытия:** закэшированное изображение, покрывающее меньше 95 % области, было
  сохранено, пока пролёты того дня ещё поступали, поэтому оно скачивается заново. Изображение,
  в котором данные есть меньше чем в 50 % площади, отвергается.
- Имя области входит в идентификатор гранулы, поэтому вырезка для каждой области кэшируется
  отдельно.

### 3.4 NASA Earthdata (`viirs_l1b`)

[viirs_l1b.py](satview/sources/viirs_l1b.py) скачивает исходные файлы полос обзора VIIRS
уровня 1B.

**Аутентификация.** Используется токен из `EARTHDATA_TOKEN`. Если он не задан, токен создаётся:

```
POST https://urs.earthdata.nasa.gov/api/users/find_or_create_token
     HTTP Basic username:password, Accept: application/json
→ {"access_token": "<JWT>", …}
```

**Поиск.** `earthaccess.search_data()` обращается к Common Metadata Repository (CMR) NASA и
ищет гранулы по `short_name`, охватывающему прямоугольнику (lon/lat-прямоугольник области),
окну времени и `day_night_flag=day`. Читаются все страницы результатов (`count=-1`). Для каждого
спутника ищутся две коллекции:

| Спутник | Яркости (M-каналы) | Геопривязка |
| --- | --- | --- |
| Suomi NPP | `VNP02MOD` | `VNP03MOD` |
| NOAA-20 | `VJ102MOD` | `VJ103MOD` |
| NOAA-21 | `VJ202MOD` | `VJ203MOD` |

При `nrt: true` к именам добавляется суффикс `_NRT`. Тогда файлы берутся из LANCE, системы
почти реального времени, через ~3 ч после пролёта вместо ~6–12 ч.

satview нужны M-каналы (750 м), потому что в файлах I-каналов (`02IMG`, 375 м) нет синего
канала. Каждая гранула яркостей связывается со своей гранулой геопривязки по временному ключу в
имени файла, например `VJ102MOD.A2026303.1130.021.….nc` → `A2026303.1130` (год, номер дня в
году, ЧЧММ). Гранула без пары пропускается. Из метаданных UMM-JSON satview берёт время начала и
конца (`TemporalExtent`) и контур покрытия (`GPolygons` или `BoundingRectangles`). По ним
выбирается пролёт (раздел 4.2).

**Скачивание.** Для каждой гранулы выбранного пролёта satview скачивает первую ссылку на данные
с заголовком `Authorization: Bearer <токен>`. Сервер данных перенаправляет в хранилище на другом
хосте, и `requests` убирает там этот заголовок, чего хранилище и требует. Гранула длиной
6 минут — это около 200 МБ яркостей и 55 МБ геопривязки. Пролёт над Израилем обычно занимает две
гранулы, то есть около 500 МБ.

**Проверка доступа.** Проверяется, что коллекции существуют в CMR. Токен (это JWT)
расшифровывается, чтобы узнать срок его действия. Затем на URL недавней гранулы отправляется
`GET` без перехода по перенаправлениям, и читаются только заголовки:

- перенаправление на `…/profiles/licenses` значит, что лицензия LANCE ещё не принята (нужно
  один раз открыть этот URL в браузере);
- 401/403 или перенаправление на `urs.earthdata.nasa.gov` значит, что токен отвергнут.

Используется `GET`, а не `HEAD`, потому что LANCE отвечает на `HEAD` кодом 200 в любом случае.

### 3.5 Copernicus Data Space Ecosystem (`sentinel3_olci`)

[sentinel3_olci.py](satview/sources/sentinel3_olci.py) обращается к OData API CDSE напрямую.

**Поиск** (без входа):

```
GET https://catalogue.dataspace.copernicus.eu/odata/v1/Products
    ?$filter=Collection/Name eq 'SENTINEL-3'
        and Attributes/OData.CSC.StringAttribute/any(att:att/Name eq 'productType'
            and att/OData.CSC.StringAttribute/Value eq 'OL_1_EFR___')
        and OData.CSC.Intersects(area=geography'SRID=4326;POLYGON((…прямоугольник области…))')
        and ContentDate/Start gt 2026-10-29T10:00:00.000Z
        and ContentDate/Start lt 2026-10-31T10:00:00.000Z
    &$orderby=ContentDate/Start desc&$top=1000
```

`OL_1_EFR___` — это OLCI уровня 1B в полном разрешении (Earth-observation Full Resolution,
300 м). У каждого результата есть `Name` (`S3A_OL_1_EFR____<начало>_<конец>_<создан>_…_NR_004.SEN3`),
`Id`, `ContentDate`, контур покрытия `GeoFootprint` в GeoJSON и флаг `Online`.

Один и тот же кадр часто публикуется до трёх раз, по мере улучшения обработки:

- NR (near real time — почти реальное время, часы);
- ST (short time critical — дни);
- NT (non time critical — недели).

Для каждой пары (спутник, время начала) satview оставляет лучший вариант: NT > ST > NR.
Продукты не в сети (offline) пропускаются.

**Токен** (только если какого-то файла действительно нет в кэше):

```
POST https://identity.dataspace.copernicus.eu/auth/realms/CDSE/protocol/openid-connect/token
     форма: client_id=cdse-public, grant_type=password, username=…, password=…
→ {"access_token": …}
```

**Скачивание отдельных файлов.** Полный кадр весит ~700 МБ, но для истинных цветов нужны
только 3 канала из 21 и геометрия. satview запрашивает каждый файл через дерево узлов продукта:

```
GET https://download.dataspace.copernicus.eu/odata/v1/Products(<Id>)/Nodes(<Name>)/Nodes(<файл>)/$value
    Authorization: Bearer <токен>        (сохраняется при каждом перенаправлении)
```

Файлы такие:

- `Oa03_radiance.nc`, `Oa06_radiance.nc`, `Oa08_radiance.nc` (442, 560 и 665 нм);
- `geo_coordinates.nc` (широта и долгота каждого пикселя);
- `tie_geometries.nc` (углы Солнца и наблюдения, для коррекции рэлеевского рассеяния);
- `instrument_data.nc` (солнечный поток, чтобы перевести яркость в коэффициент отражения).

Это ~150 МБ на 3-минутный кадр. Файлы складываются в папку `<Name>.SEN3/`, как того ожидает
читатель Satpy.

**Проверка доступа:** вход и подсчёт кадров над областью за последние 3 дня.

### 3.6 Каталоги STAC и cloud-optimized GeoTIFF (`sentinel2_msi`, `landsat_oli`)

[stac.py](satview/sources/stac.py) обслуживает оба источника. Они отличаются только каталогом,
коллекцией и названиями платформ:

| | Sentinel-2 | Landsat |
| --- | --- | --- |
| Каталог | `https://earth-search.aws.element84.com/v1` | `https://planetarycomputer.microsoft.com/api/stac/v1` |
| Коллекция | `sentinel-2-c1-l2a` (уровень 2A, отражение поверхности) | `landsat-c2-l2` (Collection 2, уровень 2, отражение поверхности) |
| Собственный пиксель | 10 м | 30 м |
| Размер тайла | 110 км (тайл MGRS) | 185 км (сцена WRS-2) |
| Глубина поиска для `latest` | 10 дней | 30 дней |
| Допуск для `at` | ± 3 дня | ± 8 дней |
| Доступ к файлам | открытый | анонимный SAS-токен |

**Поиск** (STAC API, без входа):

```
POST <каталог>/search
{"collections": ["sentinel-2-c1-l2a"], "bbox": [33.8, 29.0, 36.2, 33.6],
 "datetime": "2026-10-21T10:00:00Z/2026-10-31T10:00:00Z", "limit": 100}
```

Ответ — это GeoJSON FeatureCollection. Каждый объект («item») — один тайл, у которого есть
`properties.datetime`, `properties.platform` (`sentinel-2b`, `landsat-9`, …), контур покрытия
`geometry` и ресурсы (`assets`) с именами `red`, `green`, `blue`. У каждого ресурса есть URL
одноканального файла COG и запись `raster:bands` со значениями `scale` и `offset`. Следующие
страницы читаются по ссылке `next`. Её `body` может быть неполным (`"merge": true`); в этом
случае он объединяется с телом предыдущего запроса.

**Токен Planetary Computer.** URL файлов в Azure Blob Storage требуют краткосрочного SAS-токена.
Он бесплатный и анонимный:

```
GET https://planetarycomputer.microsoft.com/api/sas/v1/token/landsat-c2-l2
→ {"token": "st=…&se=…&sig=…", "msft:expiry": "2026-10-31T11:00:00Z"}
```

Токен добавляется к URL каждого файла (`<href>?<токен>`). Он обновляется за 5 минут до
истечения. Он запрашивается один раз, до начала параллельного чтения.

**Читается только то, что нужно.** Cloud-optimized GeoTIFF (COG) хранит пиксели во внутренних
тайлах. Кроме того, он хранит *обзорные уровни* (overviews): копии с разрешением 1/2, 1/4,
1/8, … от исходного. В заголовке файла записаны смещения в байтах для всех них. rasterio/GDAL
открывает URL `https://` через `/vsicurl/` и читает только нужные диапазоны байтов HTTP-запросами
с заголовком `Range`. `read_tile()` работает так:

1. Открывает три файла каналов тайла (красный, зелёный, синий). GDAL получает указание не искать
   сопроводительные файлы (`GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR`). Он может объединять
   соседние диапазоны и отправлять несколько диапазонов в одном запросе, и повторяет запрос до
   4 раз.
2. Выбирает обзорный уровень: наибольший коэффициент прореживания `f`, при котором
   `f × собственный пиксель ≤ шаг сетки`. Для Sentinel-2 и сетки 100 м это обычно уровень 8×
   (80 м). Для Landsat — уровень 2× (60 м).
3. Переводит границы области из lon/lat в собственную систему координат тайла (его зону UTM,
   21 точка на сторону). Превращает их в окно пикселей. Округляет окно наружу до целых пикселей
   обзорного уровня и обрезает по границам файла.
4. Читает окно с `out_shape` = окно ÷ `f`. Тогда GDAL берёт данные из этого обзорного уровня
   методом ближайшего соседа, и хранимые значения не меняются.
5. Записывает три канала в GeoTIFF в памяти: хранимые значения uint16, nodata 0, сжатие
   deflate, scale и offset в метаданных каналов и геопривязка окна. Именно эти байты кэшируются,
   в файл `<id объекта>_<область>_<шаг>m.tif`.

Восемь тайлов читаются параллельно (`ThreadPoolExecutor(8)`). Пролёт Sentinel-2 из 24 тайлов
обходится примерно в 130 МБ и ~30 с, вместо нескольких гигабайт для полных файлов.

## 4. Выбор снимков

### 4.1 Геостационарные источники

Каждый скан покрывает область целиком, поэтому вопрос только во времени. См. `select_times()`
в разделе 2.2.

### 4.2 Полярные спутники: объединение гранул в пролёты

[polar.py](satview/sources/polar.py) используется общим для VIIRS L1B, OLCI, Sentinel-2 и
Landsat.

**Окно поиска.**

- `latest`: последние 48 часов, куда всегда входят вчерашние полуденные пролёты. Sentinel-2
  использует 10 дней, а Landsat — 30 дней, из-за периода повторного обзора и задержки
  публикации.
- `at`: ± 12 ч (± 3 дня для Sentinel-2, ± 8 дней для Landsat).
- `range`: ровно от начала до конца.

**Записи.** Каждый результат поиска становится записью `Record`: спутник, начало, конец,
многоугольники контура покрытия и метаданные сервера.

**Пролёты.** Один пролёт над Израилем может быть разбит на несколько файлов: две 6-минутные
гранулы VIIRS, два 3-минутных кадра OLCI или до 24 тайлов Sentinel-2. `group_passes()`
сортирует записи по (спутник, время начала). Запись присоединяется к предыдущему пролёту, если
она с того же спутника и начинается не позже чем через заданный промежуток после конца
предыдущей. Промежуток — 2 мин для VIIRS и STAC и 1 мин для OLCI.

**Покрытие области.** `coverage()` накладывает на lon/lat-прямоугольник области сетку
24 × 24 контрольных точек. Считается доля точек, попавших внутрь хотя бы одного многоугольника
контура пролёта. Проверка «точка в многоугольнике» использует правило чётности (метод
луча), векторизованное через NumPy сразу для всех 576 точек: для каждого ребра многоугольника
точка меняет состояние «внутри», если горизонтальный луч из неё пересекает это ребро.

**Отклонение от надира.** `nadir_offset` — расстояние в градусах между центром области и центром
контура покрытия. Разница долгот умножается на cos(широты). Чем меньше значение, тем ближе
спутник прошёл прямо над головой, а значит, пиксели меньше и искажения на краю полосы обзора
слабее.

**Выбор.** `choose_passes()`:

1. оставляет пролёты, которые покрывают не меньше `min_coverage` (по умолчанию 60 %) области
   и начинаются в светлое время (Солнце ≥ 5° в центре области);
2. для `range` оставляет только пролёты внутри диапазона;
3. для `at` возвращает один пролёт, ближайший по времени;
4. в остальных случаях группирует пролёты по суткам UTC. Для `latest` берутся последние сутки,
   для `range` — все сутки. При `pick: best` победителем суток становится пролёт с наибольшим
   покрытием, округлённым до шагов по 10 %, а при равенстве — с наименьшим отклонением от
   надира. При `pick: all` остаются все пролёты суток.

Благодаря округлению покрытия пролёт ближе к надиру выигрывает у пролёта, который покрывает
лишь немного большую часть области.

## 5. От исходных данных к RGB-изображению

Есть три пути от скачанных файлов к `Image` (RGBA на целевой сетке):

| Путь | Кто использует | Функция |
| --- | --- | --- |
| Satpy | FCI, SEVIRI, VIIRS L1B, OLCI | `pipeline.satpy_image()` |
| Простой пересчёт из lon/lat | GIBS | `pipeline.resample_latlon()` |
| Мозаика коэффициентов отражения | Sentinel-2, Landsat | `stac.mosaic()` + `pipeline.reflectance_image()` |

### 5.1 Форматы входных файлов

| Источник | Формат | Что внутри |
| --- | --- | --- |
| FCI | NetCDF-4 / HDF5, по файлу на полосу BODY. Сжат фильтрами HDF5, которые регистрирует пакет `hdf5plugin`. | Сырые отсчёты 16 каналов и их калибровочные коэффициенты на фиксированной геостационарной сетке. FDHSI: видимые и ближние ИК-каналы 1 км, ИК-каналы 2 км. Полоса — одна группа строк через весь диск. |
| SEVIRI | собственный формат EUMETSAT (`.nat`), MSG уровня 1.5 | 12 каналов (3 км в подспутниковой точке, HRV 1 км) на весь диск, с заголовками, в которых записаны калибровка и навигация. |
| VIIRS L1B | NetCDF-4 (`*02MOD*.nc` + `*03MOD*.nc`) | 16 M-каналов в виде масштабированных целых чисел с коэффициентами для отражения и яркости (750 м), и отдельный файл геопривязки: широта, долгота, углы Солнца и спутника для каждого пикселя полосы обзора. |
| OLCI L1B EFR | папка SAFE `*.SEN3/`, по файлу NetCDF-4 на канал и на каждый вспомогательный набор данных | Яркость по каналам (300 м), широта и долгота пикселей, углы на сетке опорных точек, солнечный поток. |
| GIBS | PNG (8-бит RGBA) в EPSG:4326 | Уже готовое изображение в истинных цветах с обработанной цветопередачей. |
| Sentinel-2 L2A | Cloud-optimized GeoTIFF, uint16, по файлу на канал, в зоне UTM тайла | Отражение поверхности × 10 000 плюс смещение (Collection 1: scale 0,0001, offset −0,1). Берётся из метаданных STAC. |
| Landsat C2 L2 | Cloud-optimized GeoTIFF, uint16, по файлу на канал | Отражение поверхности (scale 0,0000275, offset −0,2). Берётся из метаданных STAC. |
| Natural Earth | ESRI shapefile (`.shp/.shx/.dbf/.prj/.cpg`) | Ломаные (береговые линии, берега озёр, границы) и точки с атрибутами (города). |

### 5.2 Путь через Satpy

`satpy_image()` получает имя читателя, скачанные файлы, имя композита и целевую сетку:

```python
scn = Scene(reader="fci_l1c_nc", filenames=files)        # или seviri_l1b_native, viirs_l1b, olci_l1b
scn.load([composite], generate=False, upper_right_corner="NE")   # геостационарные: север вверху
scn = scn.slice(swath_slices(...))                       # только полосы обзора полярных спутников
scn.generate_possible_composites(unload=True)
dataset = scn.resample(area, resampler=...)[composite]
rgba = enhanced_rgba(dataset)
```

1. **Чтение и калибровка.** Читатель превращает сырые отсчёты в физические величины. Для
   видимых каналов это коэффициент отражения в %. Используются калибровочные коэффициенты из
   файла: отсчёты → яркость L → отражение = π·L·d² / E_sun, где d — расстояние от Земли до
   Солнца в а. е., а E_sun — солнечная освещённость в этом канале. Высота Солнца здесь ещё не
   учтена; это делает коррекция на зенитный угол Солнца (раздел 5.3). Для OLCI солнечный поток
   берётся из `instrument_data.nc`.
2. **Сначала каналы, потом композит.** `load(…, generate=False)` загружает только каналы,
   нужные композиту, но сам композит ещё не строит.
3. **Обрезка полосы обзора.** Для данных полярных спутников (`SwathDefinition`, где у каждого
   пикселя свои широта и долгота) `swath_slices()` просматривает широту и долготу каждого
   8-го пикселя. Она находит строки и столбцы, попадающие в lon/lat-границы целевой сетки,
   добавляет запас в один шаг (8 пикселей), и Satpy вырезает из полосы этот блок. Сам Satpy
   делает так только для данных на регулярной сетке (геостационарных). Без этого коррекция
   рэлеевского рассеяния по целой полосе OLCI или VIIRS потребовала бы несколько гигабайт
   памяти.
4. **Построение композита** вместе с его модификаторами (раздел 5.3).
5. **Пересчёт** на сетку UTM.
   - `nearest` (по умолчанию для VIIRS и OLCI): ближайший сосед по KD-дереву pyresample. Для
     каждого целевого пикселя берётся ближайший пиксель полосы обзора в пределах радиуса поиска.
   - `bilinear` (по умолчанию для FCI и SEVIRI): билинейная интерполяция между четырьмя
     окружающими исходными пикселями. Так на сетке 500 м не видно квадратиков пикселей
     размером 1–3 км.

   Целевые пиксели, до которых не дотягивается ни один исходный, получают NaN и потом становятся
   прозрачными.
6. **Улучшение изображения** до 8 бит (раздел 5.4).

Настройки dask: библиотека HDF5, встроенная в wheel-пакеты netCDF4, не потокобезопасна, поэтому
всё выполняется в *однопоточном* планировщике dask. Блоки по 32 МиБ снижают пиковое потребление
памяти. Область маленькая, так что по времени это почти ничего не стоит.

Заголовок картинки — `"<платформа> <прибор> · <композит>"`, например
«Meteosat-12 FCI · true color». Время — `start_time` скана.

### 5.3 Рецепты композитов (Satpy 0.60)

| Источник / композит | Красный | Зелёный | Синий | Модификаторы |
| --- | --- | --- | --- | --- |
| FCI `true_color` | `vis_06` (0,64 мкм) | *гибридный зелёный по NDVI* из `vis_05` (0,51 мкм) и `vis_08` (0,86 мкм) | `vis_04` (0,44 мкм) | коррекция на зенитный угол Солнца → рэлеевская коррекция → ослабление у терминатора |
| FCI `natural_color` | `nir_16` (1,6 мкм) | `vis_08` | `vis_06` | коррекция на зенитный угол Солнца |
| FCI `vis_06` | один канал, показывается в оттенках серого | | | коррекция на зенитный угол Солнца |
| SEVIRI `natural_color` | `IR_016` (1,6 мкм) | `VIS008` (0,8 мкм) | `VIS006` (0,6 мкм) | коррекция на зенитный угол Солнца |
| VIIRS `true_color` | `M05` (0,67 мкм) | `M04` (0,55 мкм) | `M03` (0,49 мкм) | коррекция на зенитный угол Солнца → рэлеевская коррекция |
| OLCI `true_color` | `Oa08` (665 нм) | `Oa06` (560 нм) | `Oa03` (442 нм) | коррекция эффективной длины солнечного пути → рэлеевская коррекция |

У SEVIRI нет синего канала, поэтому истинные цвета (true color) он построить не может.
В естественных цветах (natural color) ледяные облака выглядят голубыми, водяные — белыми,
растительность — зелёной, а пустыня — коричнево-розовой.

**Коррекция на зенитный угол Солнца** (`SunZenithCorrector`). Каждое значение отражения делится
на cos θ_s, где θ_s — зенитный угол Солнца. Благодаря этому яркость поверхности не зависит от
того, насколько высоко стоит Солнце. При θ_s больше 88° коррекция постепенно ослабляется. При
θ_s больше 95° данные обнуляются.

**Коррекция эффективной длины солнечного пути** (OLCI). То же, что коррекция на зенитный угол,
но вместо 1/cos θ_s используется эффективная длина пути солнечного света через искривлённую
атмосферу (Li и Shibata, 2006), поэтому у горизонта значения не уходят в бесконечность.

**Рэлеевская коррекция** (`PSPRayleighReflectance`, pyspectral). Молекулы воздуха рассеивают
синий свет гораздо сильнее красного (∝ λ⁻⁴). Это добавляет голубую дымку, которая усиливается
при наклонном пути света. Pyspectral находит рэлеевское отражение для данного канала в заранее
рассчитанной таблице. Таблица построена для стандартной атмосферы США без аэрозолей
(`rayleigh_only`) и индексируется по зенитному углу Солнца, зенитному углу спутника и
относительному азимуту. Длины волн взвешиваются функцией спектрального отклика канала.
Табличное значение вычитается из отражения. Красный канал (0,67 мкм) служит опорой по яркости,
чтобы облака оставались белыми и не желтели: где красное отражение меньше 20 %, вычитается полная
коррекция; выше коррекция умножается на `1 − (red − 20) / 80` и при 100 % становится нулевой.

**Ослабление у терминатора** (только FCI, `SunZenithReducer`). При θ_s от 80° до 90° сигнал
умножается на коэффициент, который падает от 1 до 0 (нелинейно, сила 1,3). Это плавно затемняет
зону терминатора вместо ярких красноватых артефактов, которые там даёт коррекция 1/cos θ_s.

**Гибридный зелёный по NDVI** (FCI). «Зелёный» канал FCI на 0,51 мкм лежит вне пика отражения
хлорофилла. Если использовать только его, растительность выглядит коричневой, а пустыня —
красноватой. Satpy подмешивает часть ближнего ИК-канала 0,86 мкм:

```
NDVI  = (vis_08 − vis_06) / (vis_08 + vis_06)
f     = доля vis_08: от 0,15 при NDVI 0 до 0,05 при NDVI 1,
        по нелинейной кривой (сила 3)
green = (1 − f) · vis_05 + f · vis_08
```

**Повышение резкости.** Компоновщики истинных цветов Satpy для FCI и VIIRS умеют повышать
резкость цвета по более детальному каналу. Здесь входные каналы уже имеют одинаковое разрешение
(FCI FDHSI — 1 км; у VIIRS только M-каналы, файл I01 не скачивается), так что повышение резкости
ничего не делает.

### 5.4 Улучшение изображения: от отражения к 8-битному цвету

`enhanced_rgba()` применяет стандартное улучшение Satpy, подобранное по имени и
`standard_name` набора данных. Затем вызывается `finalize(fill_value=None)`. Он переводит
диапазон 0–1 в 0–255 с обрезкой и добавляет альфа-канал, равный 0 везде, где данные — NaN.

**Истинные цвета: логарифмическое растяжение CIRA** (`cira_stretch`). Это растяжение рассчитано
на человеческое зрение: тёмные поверхности получают больше контраста, а яркие облака
сжимаются:

```
r   = отражение(%) / 100, ограничено снизу значением > 0
out = (log10(r) − log10(0.0223)) / (0.75 · (1 − log10(0.0223)))
    = (log10(r) + 1.652) / 1.989           → обрезка до 0…1, × 255
```

| Отражение | 2,2 % | 5 % | 10 % | 30 % (пустыня) | 50 % | 80 % (плотное облако) | 100 % |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Уровень на выходе | 0 | 45 | 84 | 145 | 173 | 199 | 212 |

Яркая пустыня Негев (~30 %) остаётся заметно темнее облака (~80 %). Поэтому satview строит цвета
Sentinel-2 и Landsat из коэффициентов отражения с тем же растяжением, а не берёт готовое
изображение ESA в истинных цветах (`visual`), в котором и пустыня, и облака уходят в насыщение.

**Естественные цвета (natural color):** линейное растяжение от 0 до 120 % отражения, затем гамма
1,8.

**Один канал** (`vis_06`, `VIS006`): линейное растяжение от 0 до 100 %, затем гамма 1,5.

`to_rgba()` превращает результат (режим L, LA, RGB или RGBA) в RGBA. Серый копируется в R, G и
B. Если альфа-канала нет, добавляется непрозрачный.

### 5.5 Путь GIBS

GIBS отдаёт готовое 8-битное изображение на регулярной сетке lon/lat, поэтому его нужно только
перенести на сетку UTM:

1. Чисто чёрные пиксели помечаются как «нет данных» (альфа 0), так же как прозрачные.
2. `resample_latlon()` вычисляет lon/lat центра каждого целевого пикселя
   (`area.get_lonlats()`). Затем переводит их в дробные номера строки и столбца в PNG:

   ```
   col = (lon − lon_min) / (lon_max − lon_min) · width  − 0.5
   row = (lat_max − lat) / (lat_max − lat_min) · height − 0.5
   ```

   После этого `scipy.ndimage.map_coordinates` билинейно интерполирует каждый из четырёх
   каналов (`order=1`). Позиции за пределами PNG получают 0, то есть прозрачность.
3. Заголовок — «NOAA-20 VIIRS · true color (GIBS)». Картинка помечается как *суточная*: в имени
   файла и в подписи есть только дата.

### 5.6 Путь Sentinel-2 / Landsat

1. **Мозаика** (`stac.mosaic()`). Выходной массив размером (3, строки, столбцы) заполняется
   NaN. Каждый закэшированный тайл перепроецируется из своей зоны UTM на целевую сетку функцией
   `rasterio.warp.reproject` с **усреднением** (average). Каждый целевой пиксель — это среднее
   исходных пикселей внутри него, что даёт плавное уменьшение без алиасинга. Тайл заполняет
   только те пиксели, которые всё ещё NaN и в которых все три канала содержат данные, поэтому
   там, где тайлы перекрываются, побеждает первый. Хранимые значения переводятся в отражение
   формулой `значение × scale + offset` для каждого канала.
2. **Улучшение** (`reflectance_image()`). Отражение (0–1) × 100 даёт проценты — единицы,
   которых ожидает Satpy. Массив оборачивается в массив xarray/dask с именем `true_color`,
   блоками по 1024 × 1024 пикселя (в один поток: растяжение делает несколько копий float64,
   и на всю сетку 100 м сразу понадобился бы ~1 ГБ). Применяется улучшение Satpy для
   `true_color`: то же растяжение CIRA, что и выше, поэтому цвета совпадают с VIIRS и OLCI.

Отражение поверхности уже скорректировано на атмосферу силами ESA/USGS, поэтому рэлеевская
коррекция не применяется. ESA корректирует каждый тайл Sentinel-2 отдельно, из-за чего между
тайлами могут оставаться слабые швы.

### 5.7 Подстройка цвета для отдельного источника

Необязательный параметр `enhance: {gamma, contrast, brightness}` в конфиге источника
применяется после улучшения Satpy. Все три по умолчанию равны 1, то есть «ничего не делать».
Это помогает сделать снимки разных спутников похожими:

```
v = RGB / 255
v = v ^ (1 / gamma)                            # gamma > 1 осветляет тёмные места
v = ((v − 0.5) · contrast + 0.5) · brightness
RGB = clip(round(v · 255), 0, 255)             # альфа не меняется
```

## 6. Отрисовка и сохранение картинки

[render.py](satview/render.py) превращает `Image` в итоговую картинку.

### 6.1 Фон и размер

1. Изображение RGBA накладывается на чёрный холст RGB, альфа служит маской. Места без данных
   становятся чёрными.
2. Если задан `output.width_px` (по умолчанию 1200) и он отличается от ширины сетки, картинка
   масштабируется фильтром **Ланцоша** с сохранением пропорций. При `width_px: null` остаётся
   размер сетки (476 пикселей в ширину при 500 м, 2376 пикселей при 100 м).

### 6.2 Наложения

Наложения загружаются один раз за запуск (`load_overlays()`) для lon/lat-границ области,
расширенных на 0,5°:

- **береговые линии:** `ne_10m_coastline` плюс берега из `ne_10m_lakes` (Кинерет, Мёртвое море),
  рисуются янтарным цветом `(255, 215, 64)` с альфой 230;
- **границы:** `ne_10m_admin_0_boundary_lines_land`, белым с альфой 170;
- **города** (по умолчанию выключены): `ne_10m_populated_places_simple` с населением
  (`pop_max`) не меньше 40 000, внутри области.

Из каждого shapefile берутся только фигуры, чей охватывающий прямоугольник пересекает область.
Каждая фигура разбивается на части (ломаные минимум из двух точек).

Отрисовка (`_draw_overlays()`):

1. Создаётся прозрачный слой **вдвое больше картинки**. Это суперсэмплинг: линии, нарисованные
   в двойном размере и потом уменьшенные, выглядят гладкими (со сглаживанием).
2. Каждая точка lon/lat переводится через pyproj в UTM 36N, а затем в пиксели:
   `px = (x − xmin)/(xmax − xmin) · W`, `py = (ymax − y)/(ymax − ymin) · H`.
3. Линии рисуются средствами Pillow: толщина `max(1, round(W/800 · 2))`, со скруглёнными
   стыками. Сначала рисуются границы, поверх них — береговые линии. Города рисуются белой точкой
   с чёрной обводкой, а название — справа белым текстом с чёрной обводкой.
4. Слой уменьшается до размера картинки фильтром Ланцоша и накладывается на картинку с учётом
   альфы.

### 6.3 Подпись

`_draw_label()` пишет в левом нижнем углу `"<заголовок> · YYYY-MM-DD HH:MM UTC"`. Для суточных
изображений вместо этого пишется `"YYYY-MM-DD (daily)"`. Текст белый на чёрной подложке с альфой
150. Шрифт — встроенный шрифт Pillow размером `max(12, ширина/50)` пикселей, поэтому картинки
выглядят одинаково на любом компьютере.

### 6.4 Выходные файлы

Все файлы сначала пишутся во временный `<имя>.part.<расширение>`, а затем переименовываются,
поэтому другая программа (например, отправка в Telegram) никогда не прочтёт недописанный файл.

- **PNG:** готовая картинка, в
  `output/<source>/<YYYY-MM-DD>/<source>[_<метка>]_<YYYYMMDDTHHMM>.png`. Метка различает
  продукты одного источника за одно и то же время (спутник: `noaa20`, `S3A`, `S2B`, …).
  У суточных изображений в имени только дата, поэтому у картинок разных спутников одинаковое
  время; каждый спутник получает свою папку, `output/<source>_<метка>/<YYYY-MM-DD>/`, чтобы
  «самая свежая картинка в папке» имела смысл для отправки в Telegram.
- **GeoTIFF** (`formats: [geotiff]`): `Image` в собственном разрешении сетки, без наложений и
  подписи. 4 канала uint8 (RGB + альфа), сжатие deflate, система координат EPSG:32636,
  геопривязка по границам сетки и теги TIFF `DATETIME` и `IMAGEDESCRIPTION` (подпись). Подходит
  для ГИС и для просмотра с полной детализацией.
- **Анимации** (диапазоны времени с `gif` или `mp4`). Собираются из PNG-файлов диапазона,
  включая PNG от прошлых запусков. Кадры группируются по метке и сортируются по времени; нужно
  минимум два кадра. Анимация, которая новее всех своих кадров, не пересоздаётся.
  - GIF: imageio, длительность кадра = 1000 / `animation_fps` мс, бесконечный повтор.
  - MP4: H.264 (`libx264`), `yuv420p`, качество 8. H.264 с yuv420p требует чётных размеров,
    поэтому при необходимости кадры обрезаются на один пиксель.

  Файл: `output/<source>/<source>[_<метка>]_<начало>_<конец>.<расширение>` (для суточных
  изображений в `output/<source>_<метка>/`, рядом с кадрами).

## 7. Надёжность

- **Кэширование и идемпотентность.** Исходные файлы кэшируются, а готовые картинки
  пропускаются, поэтому cron может запускать `satview run` каждые 15 минут. Трафик и процессорное
  время тратятся только на новые снимки.
- **Изоляция.** Каждый источник и каждый снимок обрабатывается в своём блоке `try`. Отказ одного
  сервера или один испорченный файл не останавливают остальные.
- **Коды завершения.** 0 — если сработал хотя бы один источник, 1 — если все отказали, 2 — при
  ошибках конфигурации или учётных данных, 130 — при Ctrl-C.
- **Журнал.** `-v` показывает отладочные сообщения (попадания в кэш, пропущенные сканы). `-vv`
  дополнительно показывает журналы и предупреждения Satpy, pyresample, eumdac и других
  библиотек, которые по умолчанию заглушены.
- **Фиксация версий.** Версия Satpy зафиксирована на 0.60.0, потому что его читатель FCI ещё в
  бета-версии. Офлайн-тест на регрессию рисует записанный образец GIBS и сравнивает результат с
  `tests/data/regression_gibs.png`.

## 8. Известные ограничения

- **Параллакс (Meteosat-12).** Спутник видит Израиль под углом из точки 0°. Вершины высоких
  облаков рисуются там, где их пересекает луч зрения, — до ~10 км к северо-востоку от точки на
  земле под ними. Это не исправляется.
- **Задержка.** Без лицензии EUMETSAT NRT в реальном времени доступны только ежечасные сканы.
  VIIRS L1B приходит через ~3 ч (NRT) или ~6–12 ч после пролёта. Sentinel-2 — через ~5 ч после
  пролёта. Landsat уровня 2 — через 1–2 недели после пролёта (для более свежих данных уровня 1
  нужна учётная запись USGS M2M, это пока не поддерживается).
- **Ночь.** Все композиты используют видимые каналы, поэтому снимки при Солнце ниже 5°
  пропускаются.
- **Швы Sentinel-2.** Атмосферная коррекция ESA, сделанная отдельно для каждого тайла, может
  оставлять слабые перепады яркости между тайлами.
